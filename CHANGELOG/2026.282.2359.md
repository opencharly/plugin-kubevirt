# 2026.282.2359 — refactor(kubevirt): deliver the containerDisk through the venue-generic TransferImageToVenue

## Summary

Consolidates the **containerDisk node delivery** onto the one venue-generic verified transfer, per the `opencharly/charly#809` recon (`sdk#351` landed the seam; there is exactly one node-venue consumer today, so the first increment is to fold the pre-existing node paths onto it).

`container_disk_node.go` used to be a **self-contained** probe+stream pair — its own `ctr -n k8s.io images ls -q` probe and its own `podman save <ref> | ssh <alias> sudo k3s ctr -n k8s.io images import -`. It is now a thin **consumer** of:

- **`deploykit.TransferImageToVenue`** — the shared verified transfer (idempotency skip, torn-overlay recovery, post-load tag) that `charly box load` and `charly vm cp-box` already run; and
- **`deploykit.NewNodeVenue`** (from `sdk#351`, `v0.2026280.1341`) — the node-store seam (`ctrOps`) — over an `SSHExecutor` to the charly-managed k3s node, with `ctrCmd = "sudo k3s ctr -n k8s.io"`.

**Store scope is a single source of truth.** The venue's probe/tag/remove use the constant `containerDiskInNodeCtr`, and the host-side load argv is now **derived from that same constant** (not a re-typed inline literal), so a future change to it moves the load and the verification together — the comment's invariant is true.

R3: **one** node-delivery implementation, not a third. The retired bespoke `containerDiskNodeImagePresent` / `containerDiskNodeImageImport` package vars are deleted; the pure target/alias gates (`containerDiskDeliveryTarget`, `containerDiskNodeAlias`) are unchanged, so the `lifecycle.go` call site is untouched. The second pre-existing path (`plugin-kube/kindcluster.go`) is tracked as the next increment of the **`charly#809` node-delivery consolidation** (that issue is the batch this PR advances), not a free-floating deferral.
