# 2026.278.1620 — fix(kubevirt): make the managed virtctl port-forward work end-to-end — the wait-for-sshd :0 timeout (R10 green)

## Summary

**The managed `virtctl port-forward` was dead for five compounding reasons**, surfacing only as a misleading 30-minute `wait-for-sshd … :0` timeout. All five are fixed in **one commit**, and the full R10 bed is **GREEN**.

| # | root cause | fix |
|---|---|---|
| 1 | **Bare `virtctl` on PATH** — absent on the host (`setsid: failed to execute virtctl`) | `resolveVirtctl()` — `$CHARLY_VIRTCTL` → `/usr/bin/virtctl` → `$PATH`, **loud** when absent |
| 2 | **Retired argv flags** — `--local-port`/`--port` (`unknown flag`) | `portForwardArgv()` — v1.9.0 **positional** argv |
| 3 | **Un-typed target** — `unsupported resource type '<name>'` | type-prefixed `vm/<name>[/<ns>] <localPort>:22` |
| 4 | **The 30-minute cause:** the forward started **before the VMI published `status.interfaces[0].ipAddress`** → virt-api dialled the empty `:22`, whose error killed the proxy listener while `virtctl` lived | **(A)** `WaitInterfaceIP()` gate before `newPortForwarder`; **(B)** a **lifetime-aware supervisor** (`portForwardSupervisorCmd`) that restarts a dead listener (not only an exit) |
| 5 | **A pre-existing double-prefixed ssh alias** — `kit.VmSshAlias(sshAlias(p))` → `charly-charly-<domain>`, which broke `check-live` | `sshAlias()` used directly (single prefix) |

Supporting changes: `portForwardStartError()` surfaces the detach's own log line; `runVirtctl()` resolves the binary via `resolveVirtctl()`; `Stop()` kills the forward's process **group**.

Host prerequisite (operator direction): installed at `/usr/bin/virtctl` (v1.9.0) and **declared as a charly package dependency** — `opencharly/charly#790` (**MERGED** `v2026.277.1742`: archlinux `virtctl-bin` optdepend + `virtctl` in the rpm/deb/apk `suggests`).

Head `929b436f2fe94ffcac62e4a795792f1ac292da48` (branch `feat/virtctl-portforward-r10`), ONE atomic commit (supersedes `#12`/`#13`/`#15`/`#17`).
