# 2026.288.2036 — fix(kubevirt): deploy onto an externally-managed cluster — explicit guest identity + the cluster template's kubeconfig

## Summary

Deploying a `kind: kubevirt` VM onto a cluster charly did not create failed in two places, both fixed
here:

1. **No guest identity.** The containerDisk box's distro and ssh user were inferred from the local
   distro, so an externally-managed cluster produced a VMI whose guest charly could not reach.
   The `kubevirt:` cluster template's `distro` / `ssh_user` are now used explicitly.
2. **The managed port-forward dialled the wrong cluster.** `virtctl port-forward` was given only
   `--context`, so a venue whose cluster the ambient `$KUBECONFIG` does not point at was dialled by
   accident. The cluster template's `kubeconfig` now reaches the argv as `--kubeconfig`.

A third fix rides along, found by running this bed: `firmware: {bootloader: efi}` emitted `secureBoot`
in neither direction, so KubeVirt's API default (`true`) decided and a plain-UEFI guest — which is what
an Ubuntu cloud image needs — was impossible to express.

4. **The managed port-forward could be REUSED into a dead VM.** The venue reuses its forward when the
   pidfile names a live process and asked nothing else. A supervisor outlives its VMI when a deploy is
   interrupted, so the next run adopted a tunnel into a VM that no longer existed and spent its entire ssh
   cap against it — measured as `plugin-kubevirt#32`: a 30m0s `wait-for-sshd` cap burned on a supervisor
   TEN HOURS old, while four such orphans held ports, one aged sixteen hours. The reuse now PROVES the
   tunnel carries this VM's ssh (`SSH-` banner, bounded by a named `sshProbeWait`; an orphaned supervisor
   happily ACCEPTS a connection and then tunnels nowhere, so a successful dial proves nothing) and reaps
   the supervisor's process GROUP when it cannot — killing only its `virtctl` child lets the detached
   `sh -c while :` loop respawn it, which is a mistake this session made by hand first.
