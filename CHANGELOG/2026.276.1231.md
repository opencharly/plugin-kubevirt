# 2026.276.1231 — fix(kubevirt): fail loudly when a named cluster: cannot resolve (diagnostic half of #8)

## Summary

`resolveClusterContext` (`candy/plugin-kubevirt/cluster.go`) swallowed **both** its error paths — the `hostProjectDir` resolve and the `kind:kubernetes` entity resolve. A `kubevirt:` step that NAMED a cluster (`cluster: <profile>`) whose resolution failed therefore silently returned, leaving `in.KubeContext == ""`; `connFromInput` then fell back to the kubeconfig `current-context` — which was `""` on the `check-kubevirt-operator` bed — and **every** `kubevirt:` probe died with the bare `no kubeconfig context selected`, while the `kube:` probes (whose plugin resolves the same profile) passed.

The author NAMED a cluster, so a resolve FAILURE is a real failure, not a legitimate miss. `resolveClusterContext` now **returns** its errors; `invokeVerb` (the `kubevirt:` check verb) and the CLI `ops()` fail **loudly**, naming the cluster and the cause. The legitimate-miss cases (no `cluster:` named; resolved-but-empty context) still fall back to the current-context.

Head `a593414abbbea1a940a3ecd4073173887f334a6f` (branch `feat/kubevirt-loud-cluster-resolve`).

Fixes `opencharly/plugin-kubevirt#8`. The same swallow was fixed for `plugin-kube`'s k3s post-provision half in `opencharly/plugin-kube#16` (merged, `v2026.276.0815`).

### Root cause (R1) — and an honest scope statement

The bed's failure was **not** actually caused by the swallow in this file. It was a **PIN**: the bed pins `plugin-kubevirt` `v2026.269.1640`, whose `go.mod` rides **`sdk v0.2026268.1823`**; that older sdk's plugin-side resolve is broken, so every `kubevirt:` probe fell through to an empty `current-context`. Rebuilding this plugin against `sdk v0.2026273.207` (which `origin/main` pins) resolves the `cluster:` correctly — `charly#730` already bumps this pin, but to a **branch**, not a merged tag.

So the **primary fix is the pin bump** (advance the pin in `charly/charly.yml` to a merged tag on the new sdk, e.g. `v2026.275.0411`), which is in `charly/charly.yml` / `charly#730`'s scope — not this repo. **This PR is the defensive diagnostic contract**: it makes a failed `cluster:` resolve LOUD (naming the profile + cause) instead of silently degrading to an empty context, which is what made the pin problem take a full bed run to find. It is deliberately NOT the claimed cause of the green run below.
