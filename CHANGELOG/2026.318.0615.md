# 2026.318.0615 — refactor(kubevirt): read the VM template through the plugin's own view

## Summary

`opencharly/spec#304` unit 6, the big consumer leg. The authored `#KubeVirt` body — and the Go type generated from it — moves into the plugin that serves the kind (`opencharly/plugin-substrate#37`, merged), so this plugin can no longer decode a template into `spec.KubeVirt`. It decodes into **its own view** now.

**`kubevirtspec.go`** carries exactly the fields this plugin reads — 26 top-level fields plus the eleven sub-types that moved with the body (`cpu`, `firmware`, `devices`, `gpu`, `network`, `port`, `migration`, `snapshot`, `input`, `host device`, `watchdog`) and the hand-written boot-medium union. The shared types the contract KEEPS are still `spec.` (`spec.VmSize`, `spec.VmCloudInit`, `spec.Step`).

**Why the refactor is safe to read**: the view uses the **authored names and JSON tags**, so all twelve renderer/lifecycle signatures changed (`spec.KubeVirt` → `kubevirtSpec`) while not one line of their logic did. The mechanical re-point touched 66 lines across ten files.

**The view is also the validation model**: this plugin owns the deep XOR checks (`OpValidate`), and it now validates its own decoded shape rather than a contract type.

### The decode itself, proven

The renderer's tests build the view in Go; the reviewer's rule (paid for in units 5 and 6) is that the DECODE must be exercised too. Two tests now cover it:

- **`TestKubevirtSpec_DecodesAuthoredBody`** decodes a representative authored body — every top-level field the plugin reads, `plan`, and the full `devices` block (`disks`, `host_devices`, `inputs`, `watchdog`, `rng`) — through the same `json.Unmarshal` the deploy path performs, and drives a render helper from the decoded value.
- **`TestKubevirtSpec_DecodesSourceArms`** decodes the four boot-medium arms one at a time (`container_disk`, `data_volume`, `pvc`, `clone`), since one fixture can only carry one `kind`.

Round 1's finding is why the second exists and why the first grew: its `devices` and `source` objects were thinner than the claim above them, so a divergent `host_devices`/`inputs` tag would have passed.
